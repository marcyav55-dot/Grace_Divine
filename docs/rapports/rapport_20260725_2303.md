# Rapport d'intervention — Grâce Divine Multiservices
**Date :** 25 juillet 2026

## 1. Contexte initial
Le formulaire de contact (`frontend/pages/Contact.jsx`) affichait un message de succès à l'utilisateur, mais n'envoyait aucune donnée vers le backend. Les messages (`nom`, `téléphone`, `message`) restaient uniquement dans la console du navigateur (`console.log`) et disparaissaient à la fermeture de la page.

## 2. Création de l'app `contact` (Django)
- Création de l'app `apps/contact` (modèle, serializer, vue, urls, admin)
- Modèle `ContactMessage` : nom, téléphone, message, date de création, statut lu/non lu
- Vue API `ContactMessageCreateView` exposée sur `POST /api/contact/send/`
- Correction d'un bug de configuration (`apps.py` : `name = "contact"` → `name = "apps.contact"`) qui empêchait Django de démarrer
- Ajout de `apps/__init__.py` manquant
- Migrations appliquées avec succès
- Route branchée dans `core/urls.py`
- Testé avec succès via `curl` : message enregistré en base (id 1, "Test")

## 3. Connexion du frontend à l'API contact
- `Contact.jsx` modifié : `handleSubmit` envoie désormais un vrai `fetch` POST vers `/api/contact/send/`
- Ajout de la gestion et de l'affichage d'un message d'erreur si l'envoi échoue
- Testé en conditions réelles : message "Test Email" bien enregistré en base (confirmé via `manage.py shell`)

## 4. Notifications email (admin) — préparé, non finalisé
- Configuration SMTP Gmail rédigée (`EMAIL_BACKEND`, `EMAIL_HOST`, mot de passe d'application requis)
- Code de `perform_create()` avec `send_mail()` préparé pour notifier l'administrateur à chaque nouveau message de contact
- **Mis en pause** à la demande : priorité donnée à la vérification du bon fonctionnement des notifications utilisateur (push) avant d'activer l'email

## 5. Notifications Push (nouveaux articles de blog)
Découverte que le système était **déjà largement implémenté** par un développeur précédent :
- Modèle `PushSubscription` (endpoint, clés p256dh/auth)
- Vue et route API `/api/content/push-subscriptions/`
- Signal Django `notify_subscribers_on_publish` (déclenché à la publication d'un article, envoie un push à tous les abonnés via `pywebpush`)
- Composant frontend `NotificationOptIn.jsx` (bannière "Activer les notifications")
- Service worker déjà présent (`public/sw.js`)

**Ce qui manquait : les clés VAPID.**
- Génération des clés VAPID (privée + publique) via `py_vapid`
- Création du fichier `.env` avec `VAPID_PRIVATE_KEY`, `VAPID_PUBLIC_KEY`, `VAPID_CLAIMS_EMAIL`
- Correction d'une clé publique obsolète codée en dur dans `NotificationOptIn.jsx` (remplacée par la vraie clé générée, synchronisée avec le backend)
- Redémarrage propre du serveur Django après avoir tué d'anciens processus bloquant le port 8000

**Résultat du test :** abonnement push testé avec succès — un `PushSubscription` a bien été enregistré en base (endpoint Firebase Cloud Messaging confirmé).

**Reste à valider :** la réception effective d'une notification push lors de la publication d'un article de blog via l'admin Django.

## 6. Incident en cours — Connexion utilisateur bloquée
Un test de connexion (compte "Marcus YAV") est resté bloqué sur "CONNEXION..." sans réponse.

**Diagnostic :**
- Le serveur Django n'était plus lancé au moment du test (confirmé via `curl` → `Could not connect to server`)
- Code frontend vérifié (`Login.jsx`, `AuthContext.jsx`, `services/api.js`) : aucune anomalie détectée, la gestion des erreurs et le `finally` sont corrects
- Conclusion probable : le blocage était uniquement dû à l'arrêt du serveur, pas à un bug de code

**Reste à faire :** confirmer que la connexion fonctionne correctement une fois le serveur Django relancé.
